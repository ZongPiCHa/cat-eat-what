# 02 · 技术设计文档（TDD）

> 版本：v0.1  
> 目标平台：微信小游戏  
> 客户端：Cocos Creator 3.8 LTS + TypeScript  
> 服务端：Node.js 20 LTS + TypeScript + WebSocket  
> 数据库：首版内存；可选 Redis；后续 PostgreSQL

---

## 1. 目标与约束

### 1.1 技术目标

- 2-4 人实时房间，从分享卡片点开即可加入。
- 第一关 60 秒跑酷，第二关 75 秒实时乱斗。
- 同省 4G/5G 下端到端延迟目标 < 150ms。
- 单实例支持 50 个活跃房间 / 200 CCU。
- 崩溃、断线、房间卡死可监控、可恢复。
- 公开上架所需：隐私合规、实名/防沉迷、审核模式。

### 1.2 关键约束

- 微信小游戏包体有大小限制，大型美术/音频放远程 CDN。
- 微信登录只能通过 `wx.login` + 服务端 `code2Session`。
- AppSecret 绝不能出现在客户端。
- 服务器域名必须 HTTPS/WSS，并在微信后台配置合法域名。
- 首版不做自由聊天、不做内购、不做广告，减少审核面。
- 公开上架需要版号；技术开发与资质申报并行。

### 1.3 非目标

- 不做跨平台（iOS/Android 原生、Web、海外）。
- 不做大规模匹配、排行榜、赛季。
- 不做帧同步/回放/观战。
- 不做复杂物理、道具、技能树。

## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 客户端引擎 | Cocos Creator 3.8 LTS | 2D 场景、动画、粒子、UI、微信小游戏导出成熟 |
| 客户端语言 | TypeScript | 与共享配置/协议类型统一，减少低级错误 |
| 网络 | WebSocket + JSON | 4 人房间数据量小，JSON 易调试 |
| 服务端 | Node.js 20 + TypeScript | 与客户端同语言，实时 I/O 友好 |
| HTTP 框架 | Fastify | 轻量、性能好、插件生态 |
| WebSocket | `ws` | 简单可控；量大后再考虑 uWebSockets.js |
| 缓存 | Redis 7（可选） | 多实例房间注册、会话、限流；首版单实例可不用 |
| 数据库 | PostgreSQL 16（后续） | 战绩、排行榜、审计；首版不落库 |
| 部署 | 腾讯云轻量 2C4G + Docker + Caddy | 成本可控、部署简单、WSS 稳定 |
| 监控 | 结构化日志 + 健康检查 + 告警 | 首版不引入重型 APM |
| 资源 | 腾讯云 COS/CDN | 美术、音频远程加载 |

### 2.1 为什么是微信小游戏，而不是小程序

- 公开上架游戏内容，小游戏是正确类目，避免「小程序伪装成工具」的审核风险。
- 小游戏有更成熟的游戏运行时、音频、触摸、性能能力。
- Cocos Creator 可直接导出微信小游戏。
- 小程序的 Canvas 方案适合原型，但不适合作为公开游戏产品的长期形态。

### 2.2 为什么不用 Unity

- 包体、启动速度、微信小游戏适配成本更高。
- 2D 休闲游戏用 Cocos 更轻。
- 团队规模小，Cocos 的 2D 工作流更直接。

### 2.3 为什么不用纯云开发数据库做实时对战

- 云数据库 `watch` 适合大厅、聊天、排行榜。
- 20Hz 动作同步需要长连接、低延迟、服务端权威计算，WebSocket 更合适。
- 首版房间状态放内存，简单可控。

## 3. 总体架构

```
┌─────────────────────────────────────────────┐
│                微信小游戏客户端               │
│                                             │
│  启动/登录 → 首页 → 大厅 → 第一关 → 第二关 → 结算 │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌───────────┐  │
│  │ UI/场景   │  │ 游戏逻辑  │  │ 网络层     │  │
│  └──────────┘  └──────────┘  └───────────┘  │
│         │             │             │       │
│         └─────── 共享配置/协议 ──────┘       │
└─────────────────────┬───────────────────────┘
                      │ WSS / HTTPS
                      ▼
┌─────────────────────────────────────────────┐
│              Node.js 服务端                  │
│                                             │
│  Fastify HTTP          WebSocket Gateway     │
│  ├─ /api/login         ├─ auth               │
│  ├─ /api/config        ├─ room manager       │
│  ├─ /healthz           ├─ level1 generator   │
│  └─ /metrics           ├─ level2 simulation  │
│                        └─ reconnect/AI       │
│                                             │
│  RoomManager（内存）                         │
│  ├─ Room 1                                  │
│  ├─ Room 2                                  │
│  └─ ...                                     │
│                                             │
│  Redis（可选） / PostgreSQL（后续）           │
└─────────────────────────────────────────────┘
```

### 3.1 数据流

1. 客户端 `wx.login` 拿 code → HTTPS `/api/login` → 服务端换 openid → 返回 JWT。
2. 客户端建立 WSS 连接 → `auth` → 服务端绑定 openid。
3. 创建/加入房间 → 服务端返回 `room_state`。
4. 选餐 → 服务端广播公开选择。
5. 房主开始 → 服务端生成第一关序列 → 广播 `game_start` / `level1_start`。
6. 第一关客户端本地模拟，定期上报进度和分数。
7. 第一关结束 → 服务端汇总 → 广播排名 → 第二关 `level2_start`。
8. 第二关客户端 30Hz 发输入，服务端 20Hz 广播快照。
9. 时间到 → 服务端计算总分 → 广播 `game_over`。
10. 结算页 → 再来一局 / 分享 / 回大厅。

## 5. 客户端设计

### 5.1 场景结构

| 场景 | 内容 |
|---|---|
| `Boot` | 初始化、版本检查、登录、资源预加载 |
| `Home` | 首页、创建/加入房间、单人练习、设置 |
| `Lobby` | 房间座位、公开选餐、邀请、开始 |
| `Level1` | 食材跑酷 |
| `Transition` | 揭晓美食、第一关排名、第二关倒计时 |
| `Level2` | 料理大乱斗 |
| `Result` | 结算、分享、再来一局 |
| `Settings` | 音效/音乐、教学、隐私、版本 |

### 5.2 客户端状态机

```
BOOT
  → HOME
  → LOBBY (create/join)
  → LEVEL1
  → TRANSITION
  → LEVEL2
  → RESULT
  → LOBBY (rematch) / HOME
```

异常状态：

- `RECONNECTING`：断线重连弹窗，可覆盖任意游戏状态。
- `BACKGROUND`：切后台，暂停本地表现，等待回前台。
- `KICKED`：房间被销毁/被移除，回首页。

### 5.3 模块划分

| 模块 | 职责 |
|---|---|
| `BootController` | 登录、配置拉取、版本检查、资源加载 |
| `AuthService` | `wx.login`、token 存储、刷新 |
| `SocketClient` | WSS 连接、心跳、重连、消息分发 |
| `RoomStore` | 房间状态、玩家列表、选餐状态 |
| `Level1Controller` | 序列、计时、动作、判定、分数 |
| `Level2Controller` | 输入采集、快照插值、表现、HUD |
| `InputController` | 按钮/摇杆/键盘映射 |
| `AudioService` | BGM/SFX、静音、切后台 |
| `UIManager` | 页面切换、弹窗、Toast |
| `ShareService` | 分享卡片、启动参数解析 |
| `AnalyticsService` | 埋点、错误上报 |
| `PrivacyService` | 隐私授权、协议展示 |
| `GameConfig` | 美食/食材/数值/协议 |

### 5.4 渲染与性能

- 设计分辨率 750×1334，`Fit Width`，适配刘海/安全区。
- 目标 60 FPS；低端机自动降到 30 FPS。
- 使用 Sprite Atlas 合图，减少 DrawCall；目标 < 80。
- 对象池复用食材、飘字、粒子，避免每帧 `instantiate/destroy`。
- 背景使用静态大图 + 少量视差层，不每帧重绘程序化纹理。
- 避免大面积 `Blend`、实时阴影、重滤镜。
- 粒子上限：同屏 < 120 个。
- 文本使用系统字体，减少字体图集。
- 资源分包：首包只放首页/大厅/第一关必要资源；第二关和音频按需加载。

### 5.5 输入

- 第一关：两个按钮 + 键盘调试；支持 0.15 秒输入缓冲。
- 第二关：虚拟摇杆（8 方向）+ 攻击/闪避按钮；支持多点触控。
- 摇杆死区 0.15；输出归一化向量。
- 按钮按下立即播放动作表现，命中以服务器为准。
- 切后台时清空输入，避免回来时角色乱走。

### 5.6 音频

- `wx.createInnerAudioContext` 管理 BGM/SFX。
- BGM 场景切换淡入淡出 0.3 秒。
- SFX 使用对象池，同音效最多同时 3 个。
- 静音开关持久化；切后台暂停 BGM。
- 首次交互后再播放音频，避免自动播放限制。

### 5.7 微信 API 使用

| 能力 | API | 用途 |
|---|---|---|
| 登录 | `wx.login` | 获取 code |
| 启动参数 | `wx.getLaunchOptionsSync` / `wx.getEnterOptionsSync` | 解析 `roomId` |
| 分享 | `wx.shareAppMessage` / `wx.onShareAppMessage` | 邀请、结果分享 |
| 震动 | `wx.vibrateShort` | 命中、错误食材 |
| 屏幕常亮 | `wx.setKeepScreenOn` | 游戏中 |
| 网络状态 | `wx.onNetworkStatusChange` | 断线提示 |
| 前后台 | `wx.onShow` / `wx.onHide` | 暂停/恢复 |
| 安全区 | `wx.getSystemInfoSync().safeArea` | UI 适配 |
| 错误 | `wx.onError` / `wx.onUnhandledRejection` | 错误上报 |
| 隐私 | `wx.requirePrivacyAuthorize` / `wx.onNeedPrivacyAuthorization` | 隐私授权 |
| 剪贴板 | `wx.setClipboardData` | 复制房间号 |

### 5.8 分享与启动参数

- 大厅分享：

```
wx.shareAppMessage({
  title: '猫猫喊你来决定今晚吃什么！',
  imageUrl: '分享封面 CDN 地址',
  query: 'roomId=7K3M9Q&from=share'
})
```

- 冷启动：`wx.getLaunchOptionsSync().query.roomId`。
- 热启动：`wx.onShow` 回调或 `wx.getEnterOptionsSync().query.roomId`。
- 解析到 `roomId` 后：
  - 已登录 → 直接 `join_room`。
  - 未登录 → 先登录，再加入。
  - 房间已开始/已满 → 提示并回首页。
- 分享文案不诱导、不承诺奖励。

### 5.9 隐私

- 收集范围：openid（服务端）、设备基础信息、游戏行为日志、崩溃日志。
- 不收集：通讯录、位置、相册、麦克风、微信头像昵称。
- 首版不要求用户授权头像昵称，猫名和猫色由系统分配。
- 首次启动展示隐私政策摘要；使用隐私 API 完成授权。
- 提供隐私政策、用户协议、数据删除联系方式。

### 5.10 错误与埋点

- 客户端错误上报到服务端 `/api/log` 或第三方（需评估隐私）。
- 关键埋点：启动、登录、创建房间、加入房间、开始、第一关完成、第二关完成、结算、再来一局、分享、错误。
- 埋点不包含敏感信息；openid 只上报哈希或内部 ID。
- 版本号、设备型号、系统版本、网络类型用于排查。

## 6. 服务端设计

### 6.1 模块

| 模块 | 职责 |
|---|---|
| `HttpServer` | `/api/login`、`/api/config`、`/healthz`、`/metrics` |
| `WsGateway` | 连接管理、鉴权、消息路由、心跳 |
| `AuthService` | code2Session、JWT 签发/校验 |
| `RoomManager` | 创建/查询/销毁房间、房间号生成 |
| `Room` | 座位、状态机、广播、计时 |
| `Level1Generator` | 食材序列生成、公平性校验 |
| `Level1Tracker` | 进度/分数记录、结束汇总 |
| `Level2Simulation` | 20Hz 权威模拟、命中判定 |
| `BotController` | 断线 AI、单人练习 AI |
| `SessionStore` | 重连令牌、座位保留 |
| `Metrics` | 房间数、CCU、延迟、错误率 |
| `Logger` | 结构化日志、请求 ID、房间 ID |

### 6.2 房间状态机

```
WAITING
  ├─ 选餐/换餐（公开）
  ├─ 玩家加入/离开
  ├─ 房主转移
  └─ 房主开始
        ↓
LEVEL1
  ├─ 倒计时 3 秒
  ├─ 本地模拟 + 进度上报
  └─ 结束汇总
        ↓
TRANSITION
  ├─ 揭晓美食
  └─ 3 秒后
        ↓
LEVEL2
  ├─ 20Hz 权威模拟
  ├─ 断线 AI
  └─ 75 秒结束
        ↓
RESULT
  ├─ 再来一局 → WAITING
  └─ 房间超时 → 销毁
```

### 6.3 房间对象

```text
Room {
  id: string                  // 6 位房间号
  hostId: string
  status: WAITING | LEVEL1 | TRANSITION | LEVEL2 | RESULT
  createdAt: number
  updatedAt: number
  players: Map<playerId, Player>
  foods: Map<playerId, foodId>
  level1: Level1State | null
  level2: Level2State | null
  result: MatchResult | null
  timers: ...
}
```

### 6.4 玩家对象

```text
Player {
  id: string                  // 内部 playerId
  openId: string              // 服务端保存，不广播
  nickname: string            // 系统生成：橘猫/奶牛猫/黑猫/三花
  catSkin: 'orange' | 'cow' | 'black' | 'calico'
  seat: 0..3
  foodId: string | null
  score: number
  level1Score: number
  level2Score: number
  connected: boolean
  lastSeenAt: number
  isBot: boolean
  botLevel: number

```

### 6.5 登录流程

```
客户端                    服务端                      微信
  │ wx.login()              │                           │
  │──── code ──────────────▶│                           │
  │                         │── code2Session ──────────▶│
  │                         │◀── openid/session_key ────│
  │                         │ 签发 JWT                   │
  │◀── token/openIdHash ────│                           │
  │                         │                           │
  │ WSS auth(token)         │                           │
  │────────────────────────▶│ 校验 JWT，绑定 openid      │
```

- AppID/AppSecret 只放服务端环境变量。
- token 有效期 2 小时；重连时可用 refresh token 或重新 `wx.login`。
- 不信任客户端传来的 openid/playerId。
- 同一 openid 重复登录：踢掉旧连接，保留座位。

### 6.6 房间号

- 6 位，字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（去掉 I/O/0/1）。
- 生成后检查内存冲突；冲突重试。
- 加入频率限制：每 IP/每 openid 每分钟 10 次。
- 房间不存在、已满、已开始分别返回不同错误码。

### 6.7 计时与 tick

- 服务端使用单调时钟计算对局时间，避免系统时间跳变。
- 第二关逻辑 tick 固定 50ms（20Hz）。
- 每个房间独立 tick，避免全局定时器互相影响。
- tick 内只做逻辑，不做网络 I/O；快照统一广播。
- 如果事件循环延迟，记录 `tickLag` 指标。

### 6.8 第一关服务端职责

- 生成食材序列（见第 7 节）。
- 记录 `startAt`、序列、每位玩家目标美食。
- 接收进度上报（每处理一个食材或每 0.5 秒）。
- 接收最终分数。
- 校验：
  - 分数不能超过已处理食材数。
  - 分数不能超过该玩家绿色食材总数。
  - 上报时间不能早于理论时间。
  - 异常数据标记、限流，不直接封禁。
- 超时 5 秒未上报的玩家，使用最后进度作为最终成绩。
- 汇总排名，广播 `level1_end`。

### 6.9 第二关服务端职责

- 创建玩家实体、出生点、朝向。
- 接收 30Hz 输入，保存最新输入和序号。
- 20Hz 固定 tick：
  - 应用移动。
  - 处理闪避、无敌帧、冷却。
  - 处理攻击前摇/判定/后摇。
  - 命中判定、扣分、击退、受击无敌。
  - 限制擂台边界。
  - 处理 0 分保护。
  - 生成快照和事件。
- 广播快照。
- 处理断线 AI。
- 时间到计算胜负。

### 6.10 AI 设计

- 单人练习：玩家 + 3 个 AI，完整两关。
- 第一关 AI：按概率正确/错误操作，分数与真人接近。
- 第二关 AI：
  - 目标选择：最近玩家。
  - 移动：保持 70-90 距离。
  - 攻击：冷却好且在范围内。
  - 闪避：被攻击时 30% 概率。
  - 难度参数：反应时间、命中率、闪避率。
- AI 不读取玩家输入，只读公开状态。
- 断线 AI 使用中等难度，避免过强或送分。

### 6.11 重连

- 服务端为每个座位保留 `reconnectToken` 30 秒。
- 客户端重连时带 token + openid + roomId。
- 服务端校验后：
  - 第一关：返回当前时间、序列、最后分数、已处理索引。
  - 第二关：返回当前完整快照、剩余时间、分数。
  - 结算：返回结果。
- 重连成功后广播「猫猫回来了」。
- 超过 30 秒：第二关 AI 继续，座位释放；第一关成绩冻结。

### 6.12 持久化

首版：

- 房间、玩家、对局状态全部放内存。
- 进程重启丢失进行中的房间，可接受。
- 记录结构化日志，便于排查。

后续：

- Redis：多实例房间注册、会话、限流、房间快照。
- PostgreSQL：战绩、排行榜、审计、分享结果。
- 每日备份，保留 30 天。

## 7. 第一关实现

### 7.1 序列生成目标

- 24 个食材。
- 所有玩家看到同一序列。
- 每位玩家绿色食材数量接近。
- 至少 20% 干扰项，保证红绿都有。
- 前 3 个放慢作为教学；保证每位玩家前 6 个食材中至少 1 个绿色、1 个红色。
- 同一食材不连续超过 2 次。

### 7.2 生成算法

```text
输入：
  players[]（2-4）
  foods：每道菜的食材集合
  N = 24
  distractorRatio = 0.25

1. 构建：
   U = 所有玩家目标美食食材的并集
   D = 干扰池中不属于 U 的食材
   sets[p] = 玩家 p 的食材集合

2. 教学目标：
   seq = [绿色食材(p1), 红色食材, 绿色食材(p1)]
   具体的绿色食材从 p1 集合中选；红色从 D 或别人的集合中选。

3. 主体生成：
   greenCount[p] = 0
   rounds = ceil((N - 3) / 玩家数)
   对每一轮 r：
     按轮换顺序遍历玩家 p：
       候选 = sets[p] 中最近未使用的食材
       优先选择「只属于 p」的食材，控制其他人的绿色数量
       如果 greenCount[p] 明显低于平均，选一个共享食材补足
       加入 seq，greenCount[p]++
     以 35% 概率插入一个 D 中的干扰项

4. 截断/补齐到 N。

5. 校验：
   - 每位玩家绿色数量差 <= 2
   - 每位玩家至少 8 个绿色
   - 干扰项 >= 4
   - 没有同一食材连续超过 2 次
   不满足则重试，最多 20 次；仍失败则使用兜底模板。

6. 打乱主体部分（保留前 3 个教学），输出食材 ID 序列。
```

### 7.3 公平性说明

- 如果只按并集随机，食材集合大的菜（火锅）会天然获得更多绿色，不公平。
- 因此要控制每位玩家的绿色数量，而不是简单随机。
- 共享食材会导致「一个食材对多个人是绿色」，算法需要统计实际绿色数量，而不是只数加入次数。
- 重试成本很低（24 个元素），可以在服务端实时生成。
- 每局生成后记录 `greenCountByPlayer`，便于复盘和调参。

### 7.4 客户端模拟

- 客户端收到 `level1_start`：
  - `sequence`: 食材 ID 数组。
  - `startAt`: 服务端时间戳。
  - `itemInterval`: 间隔配置。
  - `travelTime`: 飞行时间配置。
- 客户端用服务器时间校准本地时钟，倒计时 3 秒后开始。
- 每个食材的到达时间 = `startAt + 3000 + index * interval + travelTime`。
- 到达到时：

```
if stunned:
  skip item
else if action == JUMP:
  if correct: score += 1; eat VFX
  else: stun(); skipNext = true
else if action == DUCK:
  safe
else:
  if correct: miss
  else: stun(); skipNext = true
```

- 每次判定后上报 `level1_progress`（index、score）。
- 结束时上报 `level1_result`（score、maxIndex）。
- 客户端不做最终排名，只做本地展示。

### 7.5 服务端校验

- `score <= processedIndex`。
- `score <= greenCountByPlayer[p]`。
- 进度时间不能早于理论到达时间（允许 300ms 误差）。
- 上报频率限制：每 200ms 最多 1 次。
- 异常标记：`suspicious`，不影响朋友间游玩；公开运营可后续加回放校验。

### 7.6 时间与断线

- 第一关以服务端 `startAt` 为准，客户端不能暂停整个房间。
- 切后台：本地暂停表现；回前台按服务器时间计算已错过的食材，标记未命中。
- 断线：分数冻结；重连后从当前索引继续。
- 如果客户端崩溃重开：服务端返回最后上报分数和当前索引，客户端从当前时间继续，不补算错过的食材。

## 8. 第二关实现

### 8.1 权威模拟

- 服务器是唯一权威：位置、攻击、命中、分数。
- 客户端只发输入，不送位置/命中结果。
- 服务器 tick 20Hz，客户端输入 30Hz。
- 客户端渲染服务器快照，远程玩家插值 100ms。

### 8.2 世界与坐标

- 世界大小 1000×1000。
- 擂台边界内缩 40，玩家半径 34。
- 出生点：四角内缩 180。
- 世界坐标映射到屏幕擂台区域，等比缩放。
- 所有数值使用浮点，广播时保留 1 位小数。

### 8.3 移动

```
输入：moveX, moveY（归一化，长度 <= 1）
速度：260 单位/秒
位置 += 方向 * 速度 * dt
限制在擂台边界内
朝向 = 输入方向（长度为 0 时保持）
```

- 对角线速度归一化，避免斜向更快。
- 输入长度小于 0.15 视为 0（死区由客户端处理，服务端再 clamp）。
- 闪避期间覆盖普通移动。

### 8.4 攻击

```
状态：IDLE → WINDUP(0.18s) → ACTIVE(0.12s) → RECOVERY(0.50s) → IDLE
冷却：0.80s，从 ACTIVE 结束开始
命中判定：ACTIVE 期间，对每个目标只判定一次
范围：距离 <= 90 + 目标半径，且夹角 <= 50°
伤害：目标 -1（最低 0）
击退：220 冲量，0.2 秒衰减
受击无敌：0.6 秒
硬直：0.15 秒
```

- 攻击开始后方向锁定，不能转身取消。
- 攻击期间不能再次攻击/闪避（可配置）。
- 目标处于无敌帧时，不扣分、不击退，但播放闪避/无敌特效。
- 0 分目标仍会被击退和硬直，但不扣分。

### 8.5 闪避

```
状态：DODGE(0.22s)
速度：600 单位/秒
无敌：0.30s
冷却：1.80s
方向：摇杆方向优先，否则当前朝向
```

- 闪避期间不能攻击。
- 闪避结束回到 IDLE。
- 冷却从闪避开始计算。

### 8.6 快照

服务端每 50ms 广播：

```json
{
  "tick": 128,
  "serverTime": 1760000000000,
  "remainMs": 52000,
  "players": [
    {
      "id": "p1",
      "x": 320.5,
      "y": 410.2,
      "facing": 1.57,
      "score": 8,
      "state": "idle",
      "invuln": false,
      "protect0": false
    }
  ],
  "events": [
    { "type": "hit", "from": "p1", "to": "p2", "x": 420, "y": 500, "score": 7 }
  ]
}
```

- `events` 只发本 tick 发生的事件，客户端播放一次 VFX。
- 快照不包含 openid、token 等敏感信息。
- 4 人 × 20Hz 的 JSON 数据量很小，首版不需要二进制。

### 8.7 客户端插值

- 客户端维护快照缓冲，渲染时间 = 服务器时间 - 100ms。
- 两个快照之间线性插值位置和朝向。
- 本地玩家也先按快照渲染，保证与服务器一致；后续可加本地预测。
- 事件 VFX 在收到快照时立即播放，不等待插值。
- 如果快照间隔 > 500ms，显示网络警告并降低插值。

### 8.8 时间同步

- 客户端每 10 秒发 `ping`，带客户端时间。
- 服务端回 `pong`，带服务器时间。
- 客户端取最近 5 次中 RTT 最小的一次计算偏移。
- 渲染时钟 = 本地单调时钟 + offset。
- 断线重连后重新采样。

### 8.9 断线与 AI

- 服务端检测 3 秒无输入/心跳 → `connected=false`，AI 接管。
- AI 在服务器 tick 内运行，与真人同一套规则。
- 玩家重连 → 关闭 AI，恢复输入。
- 超时 30 秒 → 座位释放，AI 继续到本局结束。
- 结算时标记「AI 接管」。

### 8.10 平局与加时

- 75 秒结束，比较总分。
- 如果最高分并列：
  - 进入 15 秒加时，分数锁定，只判定第一次有效命中。
  - 第一次命中者获胜。
  - 加时结束仍无命中 → 双拼（并列美食都展示）。
- 加时期间不扣分，避免影响最终排名。

## 9. 网络与同步

### 9.1 连接

- WSS 地址：`wss://ws.example.com/ws`
- 连接后 5 秒内必须发送 `auth`，否则断开。
- 心跳：客户端 15 秒 `ping`，服务端 30 秒无消息断开。
- 消息最大 4KB；超过直接断开。
- 消息频率限制：每连接每秒 60 条。
- 断线后客户端指数退避重连：1s、2s、4s、8s，最多 5 次。

### 9.2 延迟预算

| 环节 | 目标 |
|---|---|
| 客户端 → 服务端 | < 50ms（同省） |
| 服务端 tick | 50ms |
| 快照广播 | < 10ms |
| 客户端插值 | 100ms |
| 端到端操作感知 | < 150ms |

- 首版不做客户端预测；如果实测手感偏重，再给本地玩家加位置预测 + 服务器校正。
- 攻击表现立即播放，命中结果以服务器事件为准；如果服务器判定未命中，客户端不扣分、不播受击。

### 9.3 消息顺序与幂等

- 每条客户端消息带 `seq`，服务端记录最新序号，丢弃过期输入。
- 房间操作带 `requestId`，重复请求返回同一结果（重连/弱网重发）。
- 快照带 `tick`，客户端丢弃旧 tick。
- 所有时间使用毫秒时间戳。

### 9.4 弱网策略

- 输入只保留最新一帧，旧输入可丢弃。
- 快照缓冲区不足时，短暂拉伸插值，不瞬移。
- 连续丢包 > 1 秒：显示「网络不太稳定」，降低特效质量。
- 断线重连优先恢复状态，不重放开局动画。

## 10. 安全与反作弊

### 10.1 身份

- JWT 由服务端签发，包含 playerId、openid hash、过期时间。
- 所有房间操作校验 JWT 和房间成员关系。
- 不信任客户端传入的 openid、分数、位置。
- 同一 openid 多连接：旧连接踢下线。

### 10.2 第一关

- 分数不能超过已处理食材数/绿色食材总数。
- 校验上报时间与序列理论时间。
- 限制上报频率。
- 公开运营后可增加输入回放/确定性校验；首版朋友局以体验为主。

### 10.3 第二关

- 服务器权威，客户端只发输入。
- 校验输入向量长度、频率、消息大小。
- 攻击冷却、命中、分数全部服务端计算。
- 房间号加入限流，防止枚举。
- 不记录/广播 openid。

### 10.4 运营安全

- 无自由聊天/UGC，首版无内容审核压力。
- 分享文案固定，不诱导。
- 昵称/猫名系统生成，不接受用户输入。
- 日志脱敏：openid 只存 hash 或内部 ID，IP 可选脱敏。
- 管理后台后续再做，首版用日志和只读接口。

## 11. 性能与容量

### 11.1 客户端

| 指标 | 目标 |
|---|---|
| 帧率 | 60 FPS（低端 30 FPS） |
| DrawCall | < 80 |
| 同屏粒子 | < 120 |
| 内存 | < 250MB |
| 首包加载 | < 5 秒（4G） |
| 场景切换 | < 1 秒 |

### 11.2 服务端

- 单房间 4 人，20Hz，每 tick 计算量很小。
- 目标单实例 50 房间 / 200 CCU。
- 估算：50 房间 × 20Hz × 4 人 × ~1KB = 4MB/s 出站，2C4G 可承受。
- 压测目标：100 个机器人房间，CPU < 60%，tick 延迟 < 20ms。
- 超过容量后水平扩展：
  - Redis 保存房间注册表。
  - 按 roomId 哈希路由到实例。
  - 或使用一致性哈希/网关转发。
- 首版单实例足够，不做复杂分片。

### 11.3 资源

- 主包尽量 < 4MB；超出放远程 CDN/分包（以平台当前限制为准）。
- 纹理图集 2048×2048，WebP/PNG。
- 音频 44.1kHz，SFX 单声道，BGM 循环。
- 远程资源带版本号，支持热更新资源清单。
