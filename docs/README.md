# 猫猫今天吃什么 · 项目文档

> 一款 2-4 人实时联机的微信小游戏：每只猫选择一道美食，通过「食材跑酷」和「料理大乱斗」两关决出胜负，赢家选的美食就是今晚的答案。

当前阶段：**设计阶段，暂不写业务代码。**

---

## 1. 已确认的产品决策

| 项目 | 结论 |
|---|---|
| 发布目标 | 公开上架微信小游戏 |
| 服务器成本 | 可以接受，按正式项目规划 |
| 选餐方式 | 公开，所有玩家实时看到彼此选择 |
| 分数下限 | 0 分，第二关不会扣成负数 |
| 平台 | 微信小游戏 |
| 客户端 | Cocos Creator 3.8 LTS + TypeScript |
| 服务端 | Node.js 20 LTS + TypeScript + WebSocket |
| 房间人数 | 2-4 人 |
| 开始方式 | 房主随时可以开始；未选餐的玩家自动随机 |
| 目标美食 | 固定 6 道：火锅、麻辣烫、盖饭、炸鸡、汉堡、披萨 |
| 第一关 | 食材跑酷，绿光跳起来吃，红光蹲下躲 |
| 第二关 | 俯视角料理大乱斗，摇杆 + 攻击 + 闪避 |
| 胜负 | 两关总分最高者获胜，赢家的美食即今晚答案 |
| 自由聊天 | 首版不做，避免内容审核和运营风险 |
| 内购/广告 | 首版不做，先验证留存与传播 |
| 审核模式 | 提供「单人练习 + 3 个机器人」，方便审核员体验完整流程 |

### 默认规则（可在开发前调整）

| 项目 | 默认值 |
|---|---|
| 平局 | 15 秒加时，先命中者胜；仍平局则「双拼」，两样都吃 |
| 第二关攻击 | 命中后对方 -1，攻击者不加分（遵循原始设计） |
| 0 分保护 | 到 0 分后仍会被击退、眩晕，但不再扣分 |
| 第一关时长 | 60 秒 / 24 个食材 |
| 第二关时长 | 75 秒 |
| 同一道菜 | 允许重复选择；全员相同则直接结算并放庆祝动画 |
| 中途加入 | 不允许，等下一局 |
| 断线 | 第二关 3 秒后 AI 接管，30 秒内可重连 |

### 待最终确认

- 游戏正式名称、图标与商标检索。
- 平局是否采用「加时 + 双拼」。
- 第二关是否给攻击者 +1（影响节奏，建议实测后定）。
- 美术最终风格与外包预算。
- 版号申报的出版单位/代理渠道。
- 团队配置与开发预算。

## 3. 一句话理解技术方案

```
玩家手机（微信小游戏 / Cocos）
  ├─ 大厅、选餐、UI
  ├─ 第一关：本地按服务器下发的食材序列模拟
  └─ 第二关：发送输入，渲染服务器快照
            │ WSS
            ▼
Node.js 房间服务器
  ├─ wx.login 登录校验
  ├─ 房间/座位/房主/重连
  ├─ 第一关序列生成与成绩校验
  └─ 第二关 20Hz 权威模拟
            │
            ├─ Redis（可选，多实例时启用）
            └─ 日志/监控
```

**核心原则：**

- 第一关以客户端模拟为主，服务器下发序列、记录进度、校验分数。
- 第二关服务器权威，客户端不参与命中判定。
- 所有 AppSecret、openid 换取的逻辑只在服务端。
- 首版不做自由聊天、不做内购、不做广告，降低审核和运营风险。

## 4. 公开上架的关键前提

公开上架微信小游戏，**版号是硬门槛**。技术开发可以并行，但资质必须尽早启动：

1. 企业主体 + 微信认证。
2. 小游戏账号、游戏类目。
3. 小程序/小游戏备案。
4. 软件著作权。
5. 游戏版号（通过出版单位申报）。
6. 实名认证与防沉迷。
7. 隐私保护指引与内容合规。
8. 提交审核并发布。

> 没有版号时，可以先发「体验版」给 2-4 个朋友测试，但不能公开推广、开广告或内购。政策会变化，所有资质要求以微信公众平台和国家新闻出版署的最新规则为准。

详细步骤见 [06-上架与合规手册.md](./06-上架与合规手册.md)。
